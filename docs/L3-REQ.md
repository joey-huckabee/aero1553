# Aero1553 — Level 3 Requirements

## Purpose

This document establishes the Level 3 (L3) SHALL-statement requirements. L3 requirements decompose each L2 into **implementation-level obligations**: specific function names, configuration keys, library calls, dependency choices, behavior under edge conditions, exact values and thresholds, and per-implementation technology constraints.

Every L3 traces to exactly one L2 parent via the `· Parent: L2-XXX-NNN` field. L3s are the layer at which requirements become directly testable against code.

## Conventions

L3 identifiers follow the format `L3-<CATEGORY>-<NNN>`. L3 statements use a compact two-line format to keep the document navigable at scale:

> **L3-XXX-NNN** · Parent: L2-XXX-NNN · Verification: T
> *Statement.*

Verification method abbreviations (DO-178 / MIL-STD vocabulary): **T** = Test, **A** = Analysis, **I** = Inspection, **D** = Demonstration. Multiple methods are comma-separated.

Three L3 categories are reserved for per-implementation technology constraints:

- `PY` — obligations that apply only to the Python implementation under `python/`
- `RS` — obligations that apply only to the Rust crate under `rust/`
- `CPP` — obligations that apply only to the C++ implementation under `cpp/`

All other L3 categories mirror the L2 category they refine (e.g., `L3-WRT-*` decomposes `L2-WRT-*`).

**Status and verification artifacts** are tracked in [`docs/TRACE-MATRIX.md`](TRACE-MATRIX.md), regenerated by `scripts/build-trace-matrix.py` from the `@pytest.mark.requirement("L3-XXX-NNN")` markers in `python/tests/`, the `/// Requirements: L3-XXX-NNN` doc-comment tags above `#[test]` items in Rust source, and the Catch2 tag strings in `cpp/tests/` (`TEST_CASE("...", "[tag][L3-XXX-NNN]")`). Each implementation uses whatever its own test framework can already select on, so every artifact the matrix names is directly runnable. This file holds only the spec content above.

## L3-WRT: CSV output and destination integrity

**L3-WRT-001** · Parent: L2-WRT-015 · Verification: T
The temporary file used by the atomic-write strategy SHALL be created **beside** the destination (same directory, so the subsequent rename is atomic) with a `.aero1553.tmp.` name prefix that makes it recognizable in directory listings. The name SHALL be unique per writer instance — derived from the process ID, a per-process monotonic counter, and a wall-clock nanosecond timestamp — and the file SHALL be created with **exclusive create** (`O_CREAT|O_EXCL`), so two writers targeting the same destination (including within one process) cannot collide on a shared temp name and clobber each other. On the near-impossible name clash the writer SHALL retry with the next unique name.

**L3-WRT-002** · Parent: L2-WRT-016 · Verification: T
When `--allow-partial` is in effect on the L1-EXIT-004 unrecoverable path, the preserved partial output SHALL use the destination path with a literal `.partial` suffix appended (e.g., destination `out.csv` becomes `out.csv.partial`). The original destination SHALL NOT be modified.

**L3-WRT-004** · Parent: L2-MRG-005 · Verification: T
The DELTA scope selector SHALL be exposed identically on both implementations as the `[merge] delta_scope` TOML key and the `--delta-scope <SCOPE>` flag on the `decode` subcommand, accepting exactly the case-insensitive names `per-file` and `global` and defaulting to `per-file`. An unrecognized name SHALL be a config error (exit `5`) from TOML and a usage error (exit `4`) from the CLI, with the same message text on both implementations. `per-file` SHALL be realized by leaving the per-reader DELTA in place — that is, by **not** recomputing it during the merge — rather than by a second implementation of the same calculation, so the guarantee that a merged record's DELTA equals its single-file-decode DELTA holds by construction rather than by coincidence.

**L3-WRT-003** · Parent: L2-WRT-022 · Verification: T
The equal-timestamp run cap SHALL be exposed identically on both implementations as the `[output] max_sort_group` TOML key and the `--max-sort-group <N>` flag on the `decode` subcommand, with the shared bounds named as constants (`MAX_SORT_GROUP_MIN` = 1, `MAX_SORT_GROUP_MAX` = 1048576) and the shared default `4096` (`DEFAULT_MAX_SORT_GROUP`). An out-of-range or non-integer value SHALL be a config error when it comes from TOML and a usage error (exit `4`) when it comes from the CLI, matching how `decode.detect_records` / `--detect-records` already behave. Both implementations SHALL emit the same validation message text so a shared config file fails identically on either.

**L3-WRT-005** · Parent: L2-WRT-023 · Verification: T
Every implementation's atomic-write helper SHALL carry the commit mode as **state set once at construction** — a `no_clobber` argument or builder on the type that owns the temp file — and SHALL route both of its commit entry points (over the destination, and onto `<destination>.partial`) through **one** internal move routine that reads it. Neither entry point SHALL spell the flush / close / move sequence out for itself.

The single-routine rule is the substance, not tidiness: before it, `commit` and `commit_partial` each wrote the sequence separately in all three implementations, and the two consequences were exactly what that shape predicts. A rule applied at one site was not applied at the other — `.partial` commits replaced unconditionally while the destination at least got a pre-flight — and the error handling drifted, so Python's `commit` wrapped its rename but not its flush. Carrying the mode as construction-time state, rather than passing it down per call, is what stops a future third commit target from being added without one.

The single routine is also what makes L2-WRT-024 hold at both targets rather than at one: the flush, the close and the move are one sequence with one error-handling path, so a stage cannot be classified in `commit` and left bare in `commit_partial`.

The mechanism reaching L2-WRT-023's atomic-no-replace property is per platform and is named in each backend rather than here, because the platforms genuinely differ: Win32 has a single call for it (`MoveFileExW` with no flags) and POSIX does not.

## L3-RDR: Reader pipeline and DELTA tracking

**L3-RDR-001** · Parent: L2-RDR-009 · Verification: T
Each implementation SHALL derive the per-RT/MSG `DELTA` key from
`(rt, subaddress, direction)` in **exactly one place**, and both the
single-file reader path and the `--delta-scope global` merge path SHALL use
that one derivation. An implementation SHALL NOT maintain a second key
representation for the same concept.

Before this was stated, Rust and Python each tracked `DELTA` twice: the reader
keyed a map by a packed integer and the merge keyed a separate map by the
`"<rt>:<sa><T|R>"` display string. The two agreed on what "the same RT/MSG"
meant, but nothing asserted it, so a change to either would have silently made
`DELTA` mean one thing in a single-file decode and another in a merged one.
Where a display spelling is also published (`MieMessage::delta_key`), a test
SHALL assert that it partitions the `(rt, subaddress, direction)` space
identically to the tracking key.

## L3-PY: Python implementation technology

**L3-PY-001** · Parent: L2-CONF-005 · Verification: I
The Python implementation SHALL support Python `>=3.10,<3.15`. Changing the supported version set is a breaking change to this requirement, not an incidental packaging edit; the CI matrix mechanics that exercise every supported version are pinned separately by L3-PY-008.

**L3-PY-002** · Parent: L2-CONF-005 · Verification: I
Python dependencies SHALL be managed by uv, with development tools declared as a PEP 735 `[dependency-groups]` table in `python/pyproject.toml`. The committed lockfile SHALL be `python/uv.lock`. CI builds SHALL use `uv sync --locked` against the committed lockfile, so an out-of-date lock fails the build rather than being silently re-resolved, and dependency resolution is reproducible.

**L3-PY-003** · Parent: L2-CONF-005 · Verification: T, I
The Python package SHALL use the `src/aero1553` layout and SHALL expose the `aero1553` console script via `[project.scripts]` (PEP 621) in `python/pyproject.toml`. (Project metadata and the console-script entry point live in the standard `[project]` table; `maturin` is the build backend, with `[tool.maturin] python-source = "src"` pointing at the `src/` layout and `module-name = "aero1553._native"` placing the compiled PyO3 extension inside the package.) The console-script registration is verified by test (`tests/test_package_api.py`, via `importlib.metadata`); the `src/` layout by inspection.

**L3-PY-004** · Parent: L2-WRT-001 · Verification: T
Python CSV generation SHALL stream rows directly to the output handle via the standard-library `csv` module with `lineterminator="\n"` (and file destinations opened with `newline=""`), satisfying L2-WRT-012 regardless of host operating system. No DataFrame or full-file buffering SHALL be used (see L3-PY-012).

**L3-PY-005** · Parent: L2-CFG-001 · Verification: I
Python TOML parsing SHALL use the standard-library `tomllib` module on Python 3.11 and newer, and SHALL fall back to the `tomli` package on Python 3.10. No other TOML parser SHALL be used.

**L3-PY-006** · Parent: L2-CLI-011 · Verification: T
Python errors SHALL inherit from a base `Aero1553Error` class, with `MieFileError` and `MieRecordError` subclasses retaining typed detail attributes. The CLI entry point (`aero1553.cli.main`) SHALL return the exit status pinned by L2-CLI-011 for each failure class, and SHALL NOT expose a Python traceback on stderr. (It runs the Rust CLI in-process, which classifies each failure itself; the Python side neither raises nor catches for the command line.)

**L3-PY-007** · Parent: L2-CONF-006 · Verification: T, I
Public Python APIs SHALL carry type annotations and SHALL be documented in module docstrings. The `aero1553` package SHALL expose its decoder entry point (`MieFileReader`) as a typed callable importable from the package root, advertised in `__all__`. The root-export and typed-callable obligations are verified by test (`tests/test_package_api.py`); the package-wide type-annotation obligation is verified by the CI-gated strict `mypy src` run, and module-docstring documentation by inspection.

**L3-PY-008** · Parent: L2-CONF-005 · Verification: I
The Python CI workflow SHALL run pytest under Python 3.10, 3.11, 3.12, 3.13, and 3.14 as a matrix. A failure in any matrix cell SHALL fail the workflow.

**L3-PY-009** · Parent: L2-RDR-020 · Verification: I
The Python reader SHALL open the input file with `mmap.mmap(fileno, 0, access=mmap.ACCESS_READ)` (or platform equivalent). Writable or copy-on-write mmap modes SHALL NOT be used.

**L3-PY-010** · Parent: L2-CLI-008 · Verification: T
Python message counting SHALL be available through the `count` subcommand (matching the Rust CLI, `L3-RS-008`), counting valid records after the config file's `[filter]` section is applied. Stdout SHALL contain only the integer record count followed by a single newline — no prose, no path, no leading or trailing whitespace beyond that newline — so the output is directly consumable in shell pipelines (`n=$(aero1553 count rec.mie)`). A human-readable status line including the input path name SHALL be written to stderr so an interactive operator still sees context; this stderr line is not gated by `--log-level` and is always emitted on a successful count.

**L3-PY-011** · Parent: L2-ERR-011 · Verification: T
Python inline error output SHALL be the default: error and SPURIOUS_DATA records appear in the same CSV as clean records, with the `ERROR` and `ERROR_CODE` columns populated per L2-ERR-010. Separate-file output SHALL be available through the `--separate-errors` flag on the `decode` subcommand (matching the Rust CLI, `L3-RS-009`). Stdout output is always inline (you cannot split stdout), so `--separate-errors` SHALL be ignored there with a WARN. The former `--inline-errors` flag SHALL NOT be accepted — it was removed when inline became the default, and passing it SHALL be a usage error (exit 4) rather than a silent no-op.

**L3-PY-012** · Parent: L2-WRT-001 · Verification: T
Python memory usage during decode SHALL be O(1) in the number of records: the writer streams each row straight to the output handle via the standard-library `csv` module with no DataFrame or full-file buffering. Constant overhead is bounded by the output stream's buffer plus the `delta` tracker, whose keys are bounded by `RT × SA × direction`. This matches the Rust guarantee (`L3-RS-012`) and is verified by a memory test asserting the write-side peak stays within a small constant factor as the record count grows ~33x.

**L3-PY-013** · Parent: L2-FLT-001 · Verification: T
The Python package SHALL provide include filters equivalent to the Rust crate (`L3-RS-010`): `--include-types`, `--include-rts`, `--include-buses`, `--include-subaddresses` on the `decode` subcommand, with the same "passes only if contained in every active include set" semantics and the same comma-separated, repeatable argument syntax. Include filters are CLI-only overrides (no config-file key), matching Rust.

**L3-PY-014** · Parent: L2-MRG-002 · Verification: T
The Python multi-file merge SHALL be implemented in `aero1553/merge.py` using the standard-library `heapq` as the k-way merge heap (no new dependency). The global-DELTA stage SHALL replace each message's `delta` by constructing a new frozen `MieMessage` via its `with_delta` helper (the earlier `dataclasses.replace` spelling erased the concrete return type for the CI-gated strict `mypy` run, so the helper rebuilds the record field by field instead). The `--glob` expansion SHALL be constrained to the single-directory `*`/`?` filename semantics shared with Rust (`L3-RS-014`) and sorted lexicographically, so the resolved input set is byte-identical across implementations. The file-count cap `MAX_MERGE_FILES` SHALL match the Rust constant.

**L3-PY-015** · Parent: L2-MRG-007 · Verification: T
The Python cross-recorder collapsing SHALL be implemented in `aero1553/merge.py` as a `_DedupWindow` helper (a `collections.deque` of `(microseconds, file_index, content-key)` survivors) driven inside `_merge_drain` before the global-DELTA stage. The content key SHALL be a tuple of the decoded Type Word, Command/Status Words, Error Word, and `data_words`. The suppressed-duplicate count SHALL be logged at INFO once the merged stream is drained. Eviction SHALL be driven by the retention predicate over the whole survivor set, not by a one-sided test on the deque front, so a lenient backward timestamp step cannot wedge it (L2-MRG-007). The `merge.collapse_duplicates` / `merge.collapse_window_us` / `merge.max_collapse_survivors` config keys and the `--collapse-duplicates` / `--collapse-window-us` / `--max-collapse-survivors` CLI flags SHALL match the Rust surface (`L3-RS-015`).

**L3-PY-016** · Parent: L2-WRT-021 · Verification: T
The Python canonical row ordering SHALL be implemented in a dedicated module `aero1553/order.py` as an `order_rows(stream, max_group)` generator, wired into `cli._build_message_stream` as the outermost wrapper around `apply_filters` on both the single-input and merge paths. The sort SHALL use `list.sort` with the key `(rt, subaddress, direction)`, relying on `list.sort` being stable and on `Direction` being an `IntEnum` whose `RECEIVE = 0` precedes `TRANSMIT = 1` — no string comparison of the rendered `MSG` label. Because the Python stream signals a mid-stream decoder failure by **raising** rather than by yielding an error value, the generator SHALL flush its buffered run from inside an `except Aero1553Error` handler and then re-raise, so an `--allow-partial` run still commits the buffered records to its `.partial`. The flush SHALL NOT be placed in a `finally` block: on an early consumer close the generator receives `GeneratorExit`, and yielding while that is propagating raises `RuntimeError` — an early-closing consumer wants no further rows, so `GeneratorExit` SHALL discard the buffer rather than flush it. The `output.max_sort_group` config key and the `--max-sort-group` flag SHALL match the Rust surface (`L3-RS-016`, `L3-WRT-003`).

**L3-PY-017** · Parent: L2-CONF-005 · Verification: T
The Python word decoders SHALL be verified **exhaustively** against the Rust implementation, not by sampled cases: every one of the 65 536 Type Words, every one of the 65 536 Command Words, and every bit position of every IRIG and Standard timestamp field SHALL be swept through an FNV-1a digest whose expected values are those printed by `rust/examples/decode_digest.rs` — the same four constants `cpp/tests/test_decode_exhaustive.cpp` pins. Each digest SHALL be accompanied by a discrimination case proving the hash reads its input, because a digest test that cannot fail reports success forever. Until v2.16.0 this check existed only in the C++ tree, so the strongest cross-implementation check in the project covered two decoders out of three.

**L3-PY-018** · Parent: L2-WRT-023 · Verification: T
The Python no-replace commit SHALL be `os.link` followed by unlinking the temp, falling back to an exclusive-create (`open(dest, "x")`) reservation plus `os.replace` when the link fails for any reason other than `FileExistsError`. `os.link` raises `FileExistsError` when the destination exists on POSIX and on Windows alike (it calls `CreateHardLinkW` there), which is the refusal; on success it publishes the complete file under its final name in one step, so a concurrent reader never observes a partial or empty destination. The fallback exists because hard links are absent on FAT/exFAT and refused by some network filesystems, and it is a fallback rather than the primary because its reservation is briefly visible as a zero-byte destination.

The unlink after a successful link SHALL be best-effort and SHALL NOT be allowed to fail the commit: the destination is committed either way, and leaving the writer's `_committed` flag unset when the unlink fails hands `close()` a second attempt at the temp.

**L3-PY-019** · Parent: L2-WRT-024 · Verification: T
`_AtomicCsvFile._close_stream` SHALL be called from **inside** the commit's exception wrapper, so a failure of the final `flush()` is reported as `MieWriterError` and the temp is unlinked. `_AtomicCsvFile.close` SHALL swallow an `OSError` from closing the stream, so that the unlink it exists to perform still runs when the buffered data cannot be written; the commit path has already reported the real error, and re-raising from cleanup would replace it with a duplicate while leaking the temp file.

This is a Python-specific requirement because the shape only arises here. Rust's `BufWriter::into_inner` returns the flush error as a value the commit already maps, and C++'s `AtomicFile::abort` is called from a destructor that cannot propagate — in both, the failure had nowhere to escape to.

## L3-RS: Rust implementation technology

**L3-RS-001** · Parent: L2-CONF-005 · Verification: I
The Rust crate SHALL declare `edition = "2024"` in `rust/Cargo.toml` and SHALL declare a Minimum Supported Rust Version (MSRV) via `rust-version`. The floor is **1.88**, and it comes from the crate's own source, not from its dependency: edition 2024 requires only 1.85, and `memmap2` 0.9 declares `rust-version = "1.65"`. The binding feature is **let-chains** (`if let` / `while let` joined by `&&`), stabilized in 1.88 and used at seven sites (`cli.rs`, `dump.rs`, `filter.rs` ×2, `merge.rs` ×2, `writer.rs`); `u64::is_multiple_of` in `reader.rs` independently requires 1.87. CI gates the declared floor with `cargo +1.88 check --all-targets`.

**L3-RS-002** · Parent: L2-CONF-005 · Verification: I
The Rust crate SHALL declare `memmap2` as its only external runtime dependency. Additional dependencies SHALL require explicit justification; argument parsing, CSV writing, TOML parsing, logging, and error types are hand-rolled by design.

**L3-RS-003** · Parent: L2-RDR-020 · Verification: I
The Rust reader SHALL open the input file via `memmap2::Mmap` (read-only). `MmapMut` and `MmapOptions::map_copy()` SHALL NOT be used.

**L3-RS-004** · Parent: L2-WRT-001 · Verification: I
Rust CSV writing SHALL stream records directly through a `Write` implementation (typically `BufWriter<File>`) without collecting all messages or rows. `Vec<MieMessage>` or `Vec<Row>` buffering in the writer is forbidden — constant memory is the design point.

**L3-RS-005** · Parent: L2-DEC-004 · Verification: I
Rust `DataWords` SHALL be a fixed-capacity inline buffer (`[u16; 32]` plus a length counter) sized for the MIL-STD-1553B per-transaction limit of 32 data words. `Vec<u16>` SHALL NOT be used for the per-record payload.

**L3-RS-006** · Parent: L2-CLI-005 · Verification: T
Rust fallible APIs SHALL return `Result<T, MieError>`. `MieError` SHALL be a single enum (not a hierarchy) with a `kind()` discriminant and structured details for file, record, and writer failures. The CLI entry point SHALL map `MieError` to non-zero exit codes per L2-CLI-011.

**L3-RS-007** · *Withdrawn.* Previously mandated static-musl SLES 12 deployment support. The ID is reserved (not reused) so historical references and the trace matrix stay coherent.

**L3-RS-008** · Parent: L2-CLI-008 · Verification: T
Rust message counting SHALL be available through the `count` subcommand. Stdout SHALL contain only the integer record count followed by a single newline — no prose, no path, no leading or trailing whitespace beyond that newline — so the output is directly consumable in shell pipelines (`n=$(aero1553 count rec.mie)`). A human-readable status line including the input path SHALL be written to stderr so an interactive operator still sees context; this stderr line is not gated by `--log-level` and is always emitted on a successful count.

**L3-RS-009** · Parent: L2-ERR-011 · Verification: T
Rust inline error output SHALL be the default. Separate-file output SHALL be available through the `--separate-errors` flag on the `decode` subcommand (matching the Python CLI, `L3-PY-011`). Stdout output SHALL force inline mode automatically (you cannot split stdout into two streams). The former `--inline-errors` flag SHALL NOT be accepted — passing it SHALL be a usage error (exit 4).

**L3-RS-010** · Parent: L2-FLT-001 · Verification: T
The Rust crate SHALL provide include filters (the complement of exclude filters) alongside exclude filters: `--include-types`, `--include-rts`, `--include-buses`, `--include-subaddresses`. A message passes only if it matches no active exclude set and is contained in every active include set. Include filters are CLI-only overrides (no config-file key). The Python package SHALL expose equivalent CLI syntax (`L3-PY-013`).

**L3-RS-011** · Parent: L2-CONF-005 · Verification: I
The Rust CI workflow SHALL enforce: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, and the configured `cargo-llvm-cov` line and region coverage floors. A failure of any of these SHALL fail the workflow.

**L3-RS-012** · Parent: L2-WRT-001 · Verification: A
Rust decode memory usage SHALL be O(1) in the record count. The writer streams rows directly to a `BufWriter` (per L3-RS-004) and the `DataWords` payload buffer is inline-fixed (per L3-RS-005); the only per-record allocation is `String` for log messages and the per-key `HashMap` entry in the DELTA tracker, which is bounded by the count of distinct RT/MSG keys (at most 32 × 32 × 2). Verified by inspection of the writer and DELTA tracker.

**L3-RS-013** · Parent: L2-CONF-006 · Verification: T
The Rust crate SHALL re-export its public decode entry point (`MieFileReader`) and core public types (`MieMessage`, plus the error and timestamp/model types) from the crate root via `pub use` (in `rust/src/lib.rs`), so downstream crates can write `use aero1553::MieFileReader` without naming internal modules. Verified by a test that imports these symbols from the crate root and asserts the root paths are the same types as their module-path definitions.

**L3-RS-014** · Parent: L2-MRG-002 · Verification: T
The Rust multi-file merge SHALL be implemented in `rust/src/merge.rs` using `std::collections::BinaryHeap` (with `std::cmp::Reverse` for min-heap behavior) as the k-way merge heap — no new external dependency (preserving `L3-RS-002`). The `--glob` expansion SHALL be a hand-rolled single-directory `*`/`?` filename matcher (no `**`, no brace expansion) reading one directory via `std::fs`, sorted lexicographically, identical to the Python semantics (`L3-PY-014`). The file-count cap SHALL be the named constant `MAX_MERGE_FILES`, shared in value with Python.

**L3-RS-015** · Parent: L2-MRG-007 · Verification: T
The Rust cross-recorder collapsing SHALL be implemented in `rust/src/merge.rs` as a `DedupWindow` (a `VecDeque` of `(microseconds, file_index, DedupKey)` survivors) driven inside `MergedRecordIter::next` before the global-DELTA stage — no new dependency. `DedupKey` SHALL derive `PartialEq`/`Eq` over the Type Word, Command/Status Words, Error Word, and the data-word slice. The suppressed-duplicate count SHALL be exposed via an `Arc<AtomicU64>` handle the CLI reads after the run. Eviction SHALL be driven by the retention predicate over the whole survivor set, not by a one-sided test on the deque front, so a lenient backward timestamp step cannot wedge it (L2-MRG-007). The `merge.collapse_duplicates` / `merge.collapse_window_us` / `merge.max_collapse_survivors` config keys and the `--collapse-duplicates` / `--collapse-window-us` / `--max-collapse-survivors` CLI flags SHALL match the Python surface (`L3-PY-015`).

**L3-RS-016** · Parent: L2-WRT-021 · Verification: T
The Rust canonical row ordering SHALL be implemented in a dedicated module `rust/src/order.rs` as an `Ordered<I>` iterator adapter reached through an `OrderIterExt::order_rows(max_group)` extension trait, mirroring the `FilterIterExt` shape already used by `filter.rs`, and wired in `cli.rs` on both the single-input and merge paths as the last adapter before the writer. Sorting SHALL use the standard library's stable `slice::sort_by_key` over a `Vec` buffer holding one equal-timestamp run — no new external dependency, preserving `L3-RS-002`. The adapter SHALL be generic over the error type (`Iterator<Item = Result<MieMessage, E>>`) so it composes with both the reader's and the merge's item types, and SHALL emit its buffered run before forwarding an `Err` item. The `output.max_sort_group` config key and the `--max-sort-group` flag SHALL match the Python surface (`L3-PY-016`, `L3-WRT-003`).

**L3-RS-017** · Parent: L2-WRT-023 · Verification: T
The Rust no-replace commit SHALL be `std::fs::hard_link` followed by `remove_file` on the temp, falling back to an exclusive-create (`OpenOptions::create_new`) reservation plus `fs::rename` when the link fails with any kind other than `AlreadyExists`. The commit mode SHALL be carried on `AtomicCsvFile` and selected by a `no_clobber(bool)` **builder**, not by a parameter added to `AtomicCsvFile::create`: `create` is public API and growing its signature is a break `cargo semver-checks` would be right to reject.

`hard_link` is what keeps this dependency-free (`L3-RS-002`). It maps to `link(2)` on POSIX and `CreateHardLinkW` on Windows, and both fail when the destination exists, so one standard-library call spans both platforms. The no-replace primitives that would be more direct — `renameat2(RENAME_NOREPLACE)`, `MoveFileExW` with no flags — have no `std` wrapper and are reachable only through `libc` or `windows-sys`, which is a dependency this crate will not take for a behaviour it can already reach.

## L3-CPP: C++ implementation technology

**L3-CPP-001** · Parent: L2-CONF-005 · Verification: I, T
The C++ implementation SHALL be written to the **C++11** standard as accepted by **GCC 4.8.5**, the system compiler of SLES 12 SP5 (ADR-0001). Conformance SHALL be verified by a CI tier that compiles **and runs the full test suite** inside a pinned GCC 4.8.5 container, not merely by a compile check — the modern-toolchain tiers cannot detect a construct that GCC 4.8.5 rejects, and a compile-only tier cannot detect a construct it miscompiles. `<regex>` SHALL NOT be used anywhere (libstdc++ did not implement it until GCC 4.9). Changing the standard or the compiler floor is a breaking change to this requirement, not an incidental build edit.

**L3-CPP-002** · Parent: L2-CONF-005 · Verification: I · Evidence: `cpp/Makefile` and `cpp/CMakeLists.txt` — neither names a link library beyond the platform's own, and the only include path outside `cpp/include` is the vendored test framework, reached via a system-include so it cannot leak into the shipped binary; `cpp/VENDORED.md` pins that framework by SHA-256 and records that it is test-only. A runtime dependency cannot be added without editing one of the two build files, both of which are read by `scripts/assert-sources-agree.sh` in CI.
The C++ implementation SHALL have **no runtime dependencies**. Argument parsing, CSV writing, TOML configuration, logging and error types SHALL be hand-rolled, matching the single-dependency discipline of the Rust crate (`L3-RS-002`) and the stdlib-only parsing of the Python package. The sole vendored dependency SHALL be a test-only framework, pinned by version and SHA-256 in `cpp/VENDORED.md` and included via a system-include path so its own diagnostics cannot trip the project's warning gates.

**L3-CPP-003** · Parent: L2-CONF-005 · Verification: I, T
The C++ tree SHALL carry two build descriptions and exactly **one** source list (ADR-0002). `cpp/Makefile` SHALL be authoritative on Linux — it is the only one that can run inside the GCC 4.8.5 fidelity container, which has no CMake and cannot install one — and `cpp/CMakeLists.txt` SHALL be authoritative for MSVC. Both SHALL derive their library sources from `cpp/sources.txt`, and a CI gate (`scripts/assert-sources-agree.sh`) SHALL fail when the two builds resolve different sets. Build output SHALL be keyed on the compiler that produced it, so the modern, fidelity and sanitizer tiers cannot overwrite one another's artifacts.

**L3-CPP-004** · Parent: L2-CONF-005 · Verification: I, T
All operating-system calls SHALL be confined to `cpp/include/mie/platform.hpp` and its two backends, `cpp/src/platform_posix.cpp` and `cpp/src/platform_win32.cpp`. Exactly five concerns SHALL cross that boundary: read-only mapping of the input, the atomic temporary-file-and-rename output strategy, directory enumeration for `--glob`, byte-exact (binary-mode) output, and path identity plus encoding. No other translation unit SHALL include an operating-system header, enforced by `scripts/assert-platform-confined.sh`.

**L3-CPP-005** · Parent: L2-WRT-012 · Verification: T
The C++ implementation SHALL emit `\n` line endings on every host. Output handles SHALL be opened in binary mode and, on Windows, standard output SHALL be switched to binary mode before any byte is written. Without this the C runtime rewrites every newline to CRLF and the byte-exact CSV oracles fail on Windows alone.

**L3-CPP-006** · Parent: L2-WRT-015 · Verification: T
The C++ atomic write SHALL rename over an existing destination using an operation with **replace** semantics. `std::rename` SHALL NOT be used: the Microsoft C runtime's `rename` fails when the destination exists, whereas the POSIX `rename(2)` and the Rust implementation's `std::fs::rename` both replace — so a port using it would be correct on Linux and silently wrong on the shipped Windows binary. Open handles SHALL be closed before the rename, because NTFS refuses to rename a file that still has one.

**L3-CPP-007** · Parent: L2-CONF-005 · Verification: I, T
The C++ implementation SHALL NOT call `setlocale`, and SHALL NOT use the locale-sensitive `<cctype>` classification functions; characters SHALL be classified with explicit ASCII range tests. The decimal separator produced by `%.6f` for the `DELTA` column is locale-dependent, so a decoder that has changed locale emits `1,234500` where the other two implementations emit `1.234500`. Enforced by `scripts/assert-locale-free.sh`.

**L3-CPP-008** · Parent: L2-WRT-014 · Verification: T
The C++ input/output collision check SHALL be symlink-safe, resolving both paths to a canonical form before comparing them, and SHALL report a collision only when both sides resolve. A destination that does not exist yet SHALL be resolved through its parent directory rather than treated as an error, since that is the ordinary case.

**L3-CPP-009** · Parent: L2-CONF-005 · Verification: T
Windows SHALL be a supported deployment target for the C++ implementation, not merely a build target (ADR-0003). Paths SHALL be carried as UTF-8 internally and widened to UTF-16 at the platform boundary so that non-ASCII paths behave as they do under the Rust implementation. The full test suite SHALL run on Windows in CI, and the shared conformance suite SHALL be exercised against the C++ binary on both Linux and Windows.

**L3-CPP-010** · Parent: L2-CONF-005 · Verification: I · Evidence: `.github/workflows/cpp-ci.yml` — each listed gate is a required job, and each fails the workflow on a non-zero exit. The two gates that could pass vacuously are pinned deliberately: `clang-tidy` runs with `--warnings-as-errors` (set on the make target, since clang-tidy exits 0 on warnings by default), and `format-check` covers both platform backends rather than only the one this host compiles. `cpp/Makefile`'s `verify-ci` target reproduces the version-sensitive gates locally with CI's tool versions.
The C++ CI workflow SHALL enforce, at error severity: the functional suite on a modern compiler and on GCC 4.8.5; AddressSanitizer, UndefinedBehaviorSanitizer and LeakSanitizer; Valgrind memcheck with leaks fatal; `cppcheck`; `clang-tidy` run with warnings promoted to errors; `clang-format`; and the three invariant gates of `L3-CPP-003`, `L3-CPP-004` and `L3-CPP-007`. A failure of any of these SHALL fail the workflow. `clang-format` SHALL cover **both** platform backends even though only one is compiled per host, because the inactive backend is otherwise checked by no tier at all.

**L3-CPP-011** · Parent: L2-WRT-001 · Verification: A · Evidence: `cpp/src/platform_common.cpp` and the two platform backends — `AtomicFile` holds a single fixed-capacity buffer (`kWriteBufferSize`) that is flushed rather than grown, and a payload larger than it bypasses the buffer entirely instead of expanding it, so output memory is bounded independently of the record count. The analysis mirrors `L3-RS-012`.
C++ decode memory usage SHALL be O(1) in the record count. Rows SHALL be streamed through a fixed-size output buffer rather than accumulated, and the per-record data-word payload SHALL be a fixed-capacity inline buffer rather than a dynamically sized container, mirroring `L3-RS-005` and `L3-RS-012`.

**L3-CPP-012** · Parent: L2-CLI-011 · Verification: T
C++ errors SHALL be represented by a single error type carrying a kind discriminant, mirroring the Rust `MieError`/`MieErrorKind` shape rather than the Python class hierarchy, with `is_record_error()` and `is_file_error()` predicates classifying exactly the same variants as their Rust counterparts. The CLI entry point SHALL map them to the exit codes pinned by L2-CLI-011 without leaking diagnostic text intended for developers.

**L3-CPP-013** · Parent: L2-CLI-011 · Verification: T
A failure raised from the C++ record stream SHALL be **thrown** and SHALL be **terminal**: the iterator SHALL latch itself closed *before* the throw, so that a caller which catches the exception and calls `next()` again receives a clean end of stream rather than a second attempt at the record that failed. This mirrors the Python generator, which is dead once it raises, and the Rust iterator, which sets `done` before yielding an `Err`. A whole-file rejection detected while the iterator is being built SHALL be raised by the first `next()` call rather than swallowed, so that an unreadable input cannot present as an empty but successful decode.

**L3-CPP-014** · Parent: L2-CLI-010 · Verification: T
Every valued C++ CLI flag SHALL accept both the space-separated (`--flag value`) and `=`-joined (`--flag=value`) spellings, and the two SHALL produce byte-identical output. A valued flag given no value SHALL be a usage error rather than being treated as an empty value or reading past the end of the argument list. A numeric flag SHALL reject any value that is not wholly numeric — a partially-numeric value such as `4x` SHALL NOT be silently truncated to the digits that parse — and SHALL reject values outside the range the corresponding configuration key accepts, so that the same number is refused identically whichever way it was supplied. A filter-list flag SHALL tolerate surrounding whitespace and a trailing separator, and an unparsable element SHALL be reported as a **usage** error naming the flag, not as a configuration error, even though the element parser is shared with the configuration loader.

**L3-CPP-015** · *Withdrawn.* Governed how the C++ build should refuse a flag or subcommand belonging to a module it had not yet ported: with a diagnostic naming the missing capability rather than "unknown option", so an operator transferring a working invocation could tell "this build does not have that yet" from "you have mistyped this". With `merge` and `dump` landed there is no unported module left for it to govern, and a requirement whose condition cannot arise is one nothing can meaningfully verify. The ID is reserved (not reused) so historical references and the trace matrix stay coherent; if the C++ tree is ever phased again, write a new one rather than reviving this.

**L3-CPP-016** · Parent: L2-CLI-011 · Verification: T
The C++ `decode` and `count` commands SHALL classify the same input condition to the same exit code as each other and as the other implementations. In particular a file that is not an MIE recording SHALL be exit 2 from both, and an unreadable input SHALL be exit 1 from both, so that a caller's pre-flight check does not depend on which subcommand it used. No failure SHALL escape the CLI entry point as an uncaught exception: a caller cannot distinguish an abnormal termination from a signal, so every failure SHALL arrive as an exit code.

**L3-CPP-017** · Parent: L2-CLI-006 · Verification: T
The C++ `count` command SHALL write the record count, and nothing else, to stdout; its human-readable sentence SHALL go to stderr. A caller capturing stdout SHALL NOT have to strip prose to obtain the number. The streams the CLI reports on SHALL be injectable, so that this contract is assertable in-process — the alternatives are descriptor redirection, which is operating-system surface this implementation confines to its platform backends (`L3-CPP-003`), and spawning a subprocess per case, which the GCC 4.8.5 and sanitizer tiers cannot do.

**L3-CPP-018** · Parent: L2-CFG-003 · Verification: T
The C++ CLI SHALL apply configuration precedence as CLI over configuration file over built-in default. A flag whose meaning is carried by its presence alone SHALL contribute an override **only when given**: contributing the negative value when absent would let the absence of `--no-clobber` silently disable an overwrite guard the operator had set in their configuration file, which is a safety property being revoked by a flag nobody typed.

**L3-CPP-019** · Parent: L2-MRG-001 · Verification: T
The C++ input-set resolution SHALL accept positional paths, a manifest, or a glob, and SHALL treat the three as mutually exclusive. A manifest SHALL preserve the file's own order — never sorting it, because stating an order is what a manifest is for — while ignoring blank lines, `#` comment lines, and surrounding blanks, and tolerating CRLF line endings, since a manifest is a text file an operator may well have written on the other platform. A glob SHALL apply its wildcards to the **filename only**, with no recursive descent, and SHALL return matches sorted lexicographically so that two hosts enumerating one directory merge it in the same order. `?` SHALL consume one whole UTF-8 **character** rather than one byte: the other two implementations match over Unicode scalar values, and a byte-wise `?` would silently disagree with them on any non-ASCII filename. A glob that matches nothing SHALL be reported distinctly from an I/O failure, so the CLI can name the pattern in a usage error.

**L3-CPP-020** · Parent: L2-MRG-002 · Verification: T
The C++ merge SHALL hold at most one record per open input, ordered on the key `(microseconds, file index, within-file sequence)`. The file index and sequence are not decoration: without them two records sharing a timestamp compare equal, the heap may return them in either order, and one input set could then produce different bytes on different runs. That key is the heap's **internal** order only — the equal-timestamp order the CSV shows is the canonical RT/MSG order of `L2-WRT-021`, which a heap key cannot produce because the heap never holds two same-timestamp records from one input at once. An input that yields no records SHALL contribute nothing rather than failing the merge.

**L3-CPP-021** · Parent: L2-MRG-003 · Verification: T
The C++ merge SHALL reject, before producing any output, an input that cannot anchor an absolute timeline: one resolving to the Standard timestamp format, or one leading with a freerun IRIG record. The diagnostic SHALL identify the offending input, because an operator merging dozens of files must know which one to remove. Interleaving such inputs would order records by a number that means something different in each file, and would do so silently.

**L3-CPP-022** · Parent: L2-MRG-007 · Verification: T
C++ cross-recorder duplicate collapsing SHALL suppress a record whose content matches one already emitted from a **different** input within the configured window. Identical content from the **same** input SHALL never be suppressed — a bus can carry the same transaction twice, and dropping the second is losing data rather than de-duplicating it. Content identity SHALL exclude timestamp, file offset, MUX and DELTA, all of which two recorders disagree on for one transaction. The window SHALL compare **absolute** time distance so that a lenient non-monotonic input cannot underflow the comparison. A suppressed duplicate SHALL NOT advance the global DELTA cursor, so that DELTA is measured over the timeline the reader can actually see.

**L3-CPP-023** · Parent: L2-MRG-006 · Verification: T
A within-file backward timestamp step SHALL fail the batch in strict mode and SHALL WARN at most **once per input** in lenient mode. Once, not per record: an input that is thoroughly out of order would otherwise bury its own diagnostic in thousands of copies of it.

**L3-CPP-024** · Parent: L2-MRG-001 · Verification: T
The C++ CLI SHALL refuse an input set larger than `MAX_MERGE_FILES` **before opening anything**, since the cap exists to keep resource use predictable and discovering it at the last file would already have consumed the descriptors it bounds. An input set that resolves to nothing SHALL be reported in terms of the method that produced it — an empty manifest, a glob that matched nothing, and no arguments at all are three different mistakes with three different remedies.

**L3-CPP-025** · Parent: L2-CLI-009 · Verification: T
The C++ record-aware dump SHALL precede each record's bytes with a decoded annotation: record number and offset, Type Word with its human label, bus and error-flag state, classified message format, timestamp, and Command Word. For a record whose Type Word error bit is set it SHALL additionally show the Error Word and its DDC description, because that is what makes the reason legible without a separate trip to the error catalogue. The format name SHALL be the SCREAMING_SNAKE spelling used by the other implementations' reports, **not** the CamelCase spelling `message_format_name` returns elsewhere — the two are different strings for the same value and conflating them silently breaks a cross-implementation diff. A record the decoder cannot classify SHALL be labelled rather than raising: this view runs on files the decoder has already rejected, so refusing to render one defeats its purpose.

**L3-CPP-026** · Parent: L2-CLI-013 · Verification: T
Each scan-stop anomaly — an invalid `word_count`, a record whose declared extent runs past end of file, and an offset overflow — SHALL be written **inline into the report** and **also logged**. Both, because the report may be piped somewhere the log is not and the log may be watched by someone who never sees the report. The scan SHALL stop at the anomaly rather than attempting to resynchronise: `decode`'s recovery walk is the tool for reading past corruption, and a dump that skipped ahead would misrepresent where the damage begins, which is the single thing this view exists to show.

**L3-CPP-027** · Parent: L2-CLI-009 · Verification: T
The C++ raw dump SHALL render a byte range as hex plus printable ASCII without decoding anything, classifying characters by explicit ASCII range rather than `<cctype>` so that a report does not depend on the locale of the host that produced it. Its bounds SHALL be **clamped, not validated**: an offset past end of file, a zero length, or a length that would overflow SHALL each yield a well-formed empty or truncated range rather than an argument error — the operator is exploring, and the empty output already says what a rejection would. A missing or zero-byte input SHALL still be refused, because an empty report over a file that does not exist is indistinguishable from a successful read of an empty one.

**L3-CPP-028** · Parent: L2-CLI-009 · Verification: T
The C++ `dump` subcommand SHALL accept `--raw`, `--offset`, `--length` and `--records`, in both the space-separated and `=`-joined spellings, and SHALL reject a negative or non-numeric value for any of them as a usage error. It SHALL take exactly **one** input: a dump is a view of one byte range, so a second path is a mistake rather than — as it is for `decode` — an invitation to merge. A command line that parses but names a file that cannot be read SHALL be a runtime error, not a usage error, so that an operator is not sent looking for a typo that is not there.

**L3-CPP-029** · Parent: L2-WRT-014 · Verification: T
A C++ multi-file merge SHALL refuse an output path that resolves to **any** of its inputs. The writer's own input/output guard takes a single path and is deliberately given none on the merge path — it receives one stream and cannot know how many files fed it — so for a merge this check is the only thing between `decode a.mie b.mie -o a.mie` and an input being truncated while it is still being read. The check SHALL be gated on whether a merge was **requested**, not on how many readers survived: `--allow-partial` can drop a multi-input merge to a single open reader, and the writer's guard is off for the whole run either way, so keying off the surviving count would leave exactly that case unguarded. This mirrors `check_output_collision` in the Rust CLI and `_check_merge_output_collision` in the Python one.

**L3-CPP-030** · Parent: L2-CONF-005 · Verification: T
Every path the C++ implementation receives or opens SHALL be treated as UTF-8 end to end. Command-line arguments SHALL be taken from the platform layer rather than from `argv`: on Windows the C runtime builds `argv` in the process ANSI codepage, so a character that codepage cannot represent is already `?` before the program runs, and no care further down can recover it. Files SHALL be opened through the platform layer rather than `std::fopen`, because the C runtime interprets a narrow path in that same codepage. Neither rule can be enforced by `scripts/assert-platform-confined.sh`, which bans OS *headers* — `argv` and `std::fopen` need none — so both are pinned by the cross-implementation differential checks instead, which is how the original defect was found: the C++ build could not open **any** file at a non-ASCII path on Windows while every Linux test passed.

**L3-CPP-031** · Parent: L2-CFG-001 · Verification: T
The C++ config loader SHALL distinguish the three ways a config path fails — the file is absent, the path names something that is not a regular file, or it exists and cannot be read — because the three have three different remedies. Collapsing them into one diagnostic, as this implementation originally did, tells an operator only that something is wrong with a path they can plainly see. The not-a-regular-file case SHALL be rejected before any read is attempted: reading a directory fails opaquely, and reading a character device can block indefinitely.

**L3-CPP-032** · Parent: L2-WRT-023 · Verification: T
`platform::AtomicFile` SHALL expose the commit mode as `set_commit_mode(CommitMode)` and SHALL report a commit through a three-valued `CommitStatus` (`COMMIT_DONE` / `COMMIT_EXISTS` / `COMMIT_ERROR`). The refusal MUST be a distinct value rather than a `false` return with an `OsError`: "the destination exists and `--no-clobber` is set" is a policy decision the writer reports as `MieError::clobber_refused`, and flattening it into the failure arm would report it to the operator as an OS error.

The no-replace mechanism is per backend and is **not** shared, because the platforms differ in what they offer:

- **Win32** SHALL call `MoveFileExW` with **no flags**, which is a natively atomic non-replacing move, failing with `ERROR_ALREADY_EXISTS`. It works on every filesystem including FAT, and needs no fallback.
- **POSIX** SHALL call `link(2)` — which fails `EEXIST` — then `unlink` the temp, falling back to an `O_CREAT|O_EXCL` reservation plus `rename` when the link fails for any other reason (FAT/exFAT and some network filesystems have no hard links). `renameat2(RENAME_NOREPLACE)` SHALL NOT be used: it needs glibc 2.28 for the wrapper and SLES 12 SP5 ships 2.22, so reaching it means a raw `syscall(SYS_renameat2, ...)` plus a hand-written fallback for every kernel without it — more OS surface, in the layer that exists to contain OS surface, for no behaviour `link(2)` does not already provide.

**L3-CPP-033** · Parent: L2-MRG-001 · Verification: T
C++ `--glob` expansion SHALL split the pattern using `platform::is_separator` rather than a literal `"/\\"` set, and SHALL filter matched entries to regular files via `platform::file_metadata`, skipping any entry that cannot be stat'ed. This is not a C++-only restatement of L2-MRG-001 but a note on where this implementation is structurally exposed: it is the only one whose directory enumeration returns bare entry names with no type information, and the only one whose path splitting is hand-written rather than inherited from a platform-aware `Path` type. Both divergences the rule now forbids — matching a directory named `archive.mie`, and splitting on a backslash under POSIX — came from those two facts.
